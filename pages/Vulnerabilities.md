# Vulnerabilities


- Oj is a library, not and end user application
 - without an application utilizing Oj there can be no vulnerability
 - does that mean it is solely up to the app, no, if using normal, if there is an exploitable bug that is exposed through normal usage that is considered a vulnerability
 - example, if the parser crashes the application due to some magic value in a field that would be expected to parse without error then that might be considered a vulnerability. It might not if there is a reasonable expectation that the developer rescue parse failures

- normal or expected usage
 - no exposure of APIs to the public, that would require some form of unfiltered capture
  - If a think layer in the app then use the safe parser
  - absolutely never use the :object mode parser, it is intended to only parse json generated by :object mode write
 - data exchange or storage behind the firewall in the private portion of a set of applications
  - writing to a database or file is from one web app is an example as is exchanging data as json using a messaging service
 - writing is always done by the app which is expected to be in control of the object being written
 - parsing is always on data already touched by an app, back to don't expose oj apis directly
 - parsers
  - modes
  - new parser types
  - callback
 - use of fibers, memory use

- what are not
 - writing extreme data, too deep, too large, bad as_json
 - parsing :object mode on json not dumped as :object mode
 - thin layer before calling the parser on a public api and not using the safe parser
  - generally a bad idea even if safe parser as it does not project against ddos attacks
